## 1. Working memory on disk — the plan the *model* re-reads

**What CC already has, and keeps.** `journal.py` (append-only JSONL, prompt
hashes, per-call provenance), `session.resume()` derived from the journal plus
the codemap, `resumable.py`, and the Continue button of 2026-10-23. That is a
stronger crash story than planning-with-files has. None of it changes.

**What it lacks.** The journal is written *for the host*. The small model never
reads it, so a 7B–24B coder loses the thread the moment its context fills — it
forgets what the task was for, which phase it is in, and what it learned three
files ago. planning-with-files' one good idea is the fix: *context window = RAM,
filesystem = disk; anything important is written to disk and read back before a
decision.* It matters **more** for a small local model than for a frontier one.

**Design.** A plan folder beside the project, `<project>\.ccoder\plan\`:

| File | Written by | Read by | Content |
|---|---|---|---|
| `task_plan.md` | the engine, from the planner's DAG + session state | the model (header of every prompt), the operator (board) | Goal (one sentence) · Next step · Current phase · one `### Phase N` per task group with exactly one `**Status:** pending/in_progress/complete/failed` line |
| `findings.md` | the engine, mirroring `note` events from the journal | the model (last N findings in the header), the operator | What was learned about *this* codebase: an API shape, a build quirk, a failing test's real cause, an operator correction |
| `progress.md` | the engine, from the journal | the operator; the model on resume only | Per-step log: attempt, model, verify result, reasoning summary (§2) |

**Why the engine writes them, not the model.** A model allowed to free-write
`task_plan.md` will corrupt its own status markers within an hour. The model
proposes (a structured `note` op → journal event), the engine renders. The
journal stays the single source of truth; the plan files are a *view* of it
the model can read. A malformed plan file is regenerated from the journal,
never repaired by hand and never trusted.

**Build items.**

- **1a `planfile.py`** — render the three files from the journal + planner;
  a validator (`validate(path) -> list[str]`) that enforces the phase/status
  format; `note` journal event kind added to `types.py` (public API, semver).
- **1b The prompt header.** Goal · Next step · Current phase · last N findings,
  bounded (default 600 tokens, a `sizing.py` budget line — the header is paid
  for by the context, so it is budgeted like everything else). Injected at the
  top of every generation, review and repair prompt. This is the small model's
  "where am I".
- **1c Resume = journal + plan + `git diff --stat`.** On `resume()` and on
  Continue: replay the journal as today, then list every file changed since
  the last journal event (`git diff --stat`, or mtime when there is no git) —
  Bill editing by hand, another session, a failed run — show the list as
  *"changed since you stopped"*, re-index those files in codemap, and only
  then continue. Today a hand edit between stop and Continue is invisible.
- **1d Gated stop.** "Finish this part, then stop" ends only at a phase
  boundary *and* after the Status line is written; a stop inside a phase
  leaves `in_progress` on disk, which is exactly what Continue reads.
- **1e One owner.** When two providers alternate (the DiffusionGemma helper,
  the writer model of the content lane), the session owns `task_plan.md`;
  helpers write only through `note`. No second plan is ever created.

**Not taken from planning-with-files.** Its Claude-Code hook plumbing
(UserPromptSubmit/PreToolUse/…); its session-history replay. CC is its own
host; it needs neither.

**Tests.** Validator fixtures (good, missing status, two statuses, a bare
checklist); the kill-at-file-3 resume of §11 phase 6 *with a hand edit of
file 2 in between* — the edit is listed, re-indexed, and the build still
completes; the header never exceeds its budget on a 4k-context model.

## 2. Reasoning in Cognitive Coder — and the bleed guard

Bill: *"We should add all of the reasoning options that chat has, for cognitive
coder … But we must also be careful that the thinking is handled in a way that
it doesn't bleed into the actual files."*

- **2a Levels.** Off · low · medium · high · xhigh, the same five as ATK chat.
  The thinking mode is chosen for the loaded model automatically (Gemma, Qwen,
  Muse …) the way ATK's `thinking.py` / `reasoning.py` already do — reached
  through `LLMPort.capabilities()` (a `reasoning` field: supported levels and
  the model's delimiters), **not** by importing ATK into the core (C1). Off
  unless enabled, as Bill decided for chat on 2026-10-29.
- **2b Default level per phase**, operator-overridable per task: Blueprint /
  planning **high** · per-file generation **low** (medium on retry) · Debug &
  Repair **high** · review **medium**. Reasoning is paid for in context; on a
  small model the header (§1b) + reasoning + code must fit, so `sizing.py`
  budgets the reasoning too.
- **2c The bleed guard — two walls, the second one deliberately paranoid.**
  Wall 1: `split_think()` on every reply before anything downstream sees it;
  the reasoning text goes to the journal (sized, hashed) and a one-line
  summary to `progress.md` — the *only* places it ever lives. Wall 2:
  `patcher.py` refuses any hunk that contains the model's reasoning
  delimiters or a `<think`/`</think` marker in any case or spacing, and
  journals the refusal as a sentence (C6). Two walls because wall 1 depends on
  knowing the model's delimiters and a new model can lie about them; wall 2
  does not care which model it was.
- **Test.** A planted `<think>` block (and a lower-case, a spaced, and a
  mid-line variant) in a generation never reaches disk, and the refusal is
  worded in the journal.

## 3. Retry this file — with a model swap

Bill: *"manually order the file to be retried, this way, i can go switch
models, and try a few if i want. Just a simple right click, retry. Is that hard
to add?"* — **No.** The per-file right-click exists (NEXT_TABS.md §5), patcher
transactions exist, the journal exists. It is a day.

- **3a The menu.** Right-click a file on the board → **Retry…** with: same
  model · swap model (the list `LLMPort.capabilities()` offers plus the host's
  swap button, §0.1) · reasoning level (§2) · *include the last failure's
  diagnostics* (on by default — the retry should know why the last attempt
  failed).
- **3b What happens.** The file's task is set back to `pending` in
  `task_plan.md` with the reason *operator retry* (journaled); the loop takes
  it next. **Undo first by default:** patcher rolls back the file's last apply
  so the retry starts from the pre-attempt state; *keep current* is the other
  option for a file that is half right.
- **3c A retry queue, not a one-shot.** Several files can be queued with
  different models; the queue drains in board order, the model swap happening
  at each boundary through the host (one model loaded at a time — Appendix
  A.2 still holds).

## 4. Task-profiled expert residency — CC's side of an inference feature

From the Strata review (2026-11-05). Strata keeps a budget of a MoE model's
experts resident and streams the rest; it saves a generic expert profile.
The better, original version — and the one that is *ours*: **profile the
experts a task actually fires, then pin those.** A coding build has a stable,
repeatable expert footprint; chat does not. CC is therefore the right first
workload to profile.

- **4a CC's side (small).** A `expert_profile` capability flag on `LLMPort`;
  when the engine reports router decisions, a recorder accumulates per-layer
  expert hit counts across a build and writes
  `<project>\.ccoder\plan\expert_profile.json` (model id, quant, layer → top
  experts, sample count). On the next build with the same model, the profile
  is handed back through the port before the first prompt. Without the engine
  hook, every part of this is a no-op and nothing is logged as missing.
- **4b The engine side is not here.** It belongs in Bill's llama.cpp fork (the
  diffusion fork), not in a Strata fork — the decision and its reasons are in
  the 2026-11-05 chat / `INFERENCE_ENGINE_DECISION.md`. Dense models: no-op.
- **4c Measure before trusting.** `bench.py` gains a row: same prompt, same
  seed, tok/s and prompt_ms with and without the profile, on a Qwen3-30B/35B-
  A3B-class GGUF on Bill's box (16 GB VRAM, 64 GB RAM — the only MoE sizes
  that fit). If the gain is not there, the profile is kept for the record and
  the pinning is left off.

## 8. Ideas from other harnesses — Hermes Agent, DSH, Pi (added 2026-11-05, later)

Bill: *"It's not that I want to use those harnesses, only that they may have
ideas that we can incorporate into ATK."* Source: a Discord thread of
2026-10-30 (Solly9Billion, Softology) comparing Hermes Agent (Nous Research's
open-source agent harness — a *client* that talks to any OpenAI/Anthropic-
compatible engine; not the Hermes models), DSH ("DeepSeek Harness", built for
DeepSeek 4, said to work with other local models) and Pi. None of them is
adopted; each lesson below is a CC item or a CC test.

- **H1. The context budget is the engine's, never the model card's.** Hermes
  set itself to 1M tokens because the Qwen3.8-FN model card says 1M, never
  compacted, and ran out of memory while the engine was set to 256K. CC reads
  `llm.capabilities()` for its budget (`context.py:104`), so the question is
  what the ATK adapter reports there. **Rule:** `capabilities().context` is
  the engine's *loaded* `n_ctx`, never the GGUF header's trained length; the
  budget is the smaller of the two, and `sizing.py` compacts against *that*.
  **Test:** a stub model whose header says 1,048,576 with an engine loaded at
  8,192 → CC budgets 8,192 and says so in the journal. Goes first in the
  order (§7) — it is a test, and the failure mode is a crash in the field.
- **H2. Stop is always allowed, always finishes, and leaves "continue" on
  disk.** Hermes could not always be closed safely when idle and is designed
  to be left running; Bill cannot leave the PC on. CC's gated stop (§1d) is
  for *phase boundaries*; this is the other half: a stop at **any** moment
  completes within a deadline (the RF engine's rule, "Stop and Exit have
  deadlines"), the journal records where it was, and the next session's
  Continue works from it. No always-on mode, ever — it is a non-goal.
- **H3. Skills distilled from finished builds.** Hermes "accumulates skills"
  as it iterates, which its users found useful for branching adjacent ideas
  off something already built. CC already has deployed skills
  (`skills.py`: markdown in `.ccoder\skills\`, into the cached prefix, sorted,
  loaded once per session). The addition: when a module builds and its tests
  pass, CC **proposes** a skill — the libraries and versions that worked, the
  build/run commands, the structure it settled on, the gotchas promoted from
  `findings.md` — as `.ccoder\skills\90-learned-<module>.md`, shown to the
  operator in the board with *Keep / Edit / Discard*. Kept skills ride into
  the next session by the mechanism that exists. A shared library
  (`D:\Analyst_Toolkit\ccoder_skills\`) for skills the operator wants in every
  project, copied in by the initializer, never loaded from outside the
  project at run time (C1/C3 — nothing reaches past the project folder
  without a visible choice). Numbered 90+ so hand-written skills win the
  budget.
- **H4. Stay narrow.** The thread's verdict on Hermes — "trying to do a
  little too much … a distraction from the matter in hand, creating working
  code" — is Bill's own rule of 2026-10-10 restated by strangers: CC's
  purpose is working code. No plugin surface, no tool sprawl, no agent that
  does the operator's whole desktop. Recorded here so the next review does
  not re-propose it.
- **H5. "Continue the last session" in plain words.** Softology's recovery
  habit: quit, restart, type *continue the last session*, and the harness
  works out what it was doing from disk. CC's Continue button does this;
  add the plain-language door — typing *continue* (or *resume*) in the chat
  tab with no active session resumes the most recent one for this project,
  after showing what it will resume (§1c's "changed since you stopped" list).
- **Not taken.** Hermes's always-on design and skill marketplace; DSH and
  Pi unread — if Bill wants them mined for ideas the way planning-with-files
  was, that is a separate pass on their source, not on a Discord summary.
